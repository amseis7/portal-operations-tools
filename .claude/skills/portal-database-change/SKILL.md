# Portal Database Change

## Purpose

Use this skill whenever a change to Portal Operations Tools affects the
persistent database schema or stored data structure.

Examples:

- adding a SQLAlchemy model;
- adding or removing a column;
- changing a relationship;
- adding a foreign key;
- adding a unique constraint;
- adding an index;
- changing persisted configuration;
- modifying the format of existing persisted data;
- modifying encrypted database fields;
- creating an Alembic migration;
- migrating existing data.

This skill provides project-specific database rules.

It does not replace:

- `/plan-eng-review`
- `/review`
- `/investigate`
- `/careful`
- `/codex`

Those provide general engineering workflows.

---

## 1. Load Project Context First

Before modifying database code, read:

```text
AGENTS.md
docs/PROJECT_MAP.md
docs/decisions/ADR-002-database-schema-migrations.md
```

Then identify the subsystem affected.

Read only the relevant system documentation:

```text
docs/systems/<subsystem>.md
```

Examples:

```text
Vault change
→ docs/systems/vault.md

VirusTotal change
→ docs/systems/virustotal.md

Umbrella change
→ docs/systems/umbrella.md
```

Do not scan every subsystem automatically.

---

## 2. Check Current Technical Debt

Inspect relevant entries in:

```text
docs/technical-debt/current.md
```

Determine whether the requested database change:

```text
does not affect known debt
preserves known debt
partially resolves known debt
fully resolves known debt
could make known debt worse
```

Do not silently fix unrelated technical debt.

---

## 3. Source of Truth

For database behavior, use this priority:

```text
1. Current SQLAlchemy models
2. Existing Alembic migrations
3. Automated tests
4. docs/systems/
5. docs/generated/
6. ADRs
7. historical specs/plans
```

Never infer the current schema solely from documentation.

Inspect the actual affected models.

---

## 4. Existing Database Architecture

The project uses:

```text
SQLAlchemy
Flask-SQLAlchemy
Flask-Migrate
Alembic
SQLite
```

Schema changes must follow the existing architecture.

Do not introduce another ORM or migration framework.

Do not modify SQLite database files manually as the implementation strategy.

---

## 5. Required Schema Change Workflow

For every schema change, follow this sequence:

```text
understand current model
        ↓
identify existing persisted data
        ↓
modify SQLAlchemy model
        ↓
create new Alembic migration
        ↓
review upgrade()
        ↓
review downgrade()
        ↓
review existing-data compatibility
        ↓
apply migration to test database
        ↓
validate application behavior
```

Do not skip migration review because an autogenerated migration appears correct.

---

## 6. Never Rewrite Historical Migrations

Existing migration files represent schema history.

Do not modify historical migrations merely to make a new change easier.

Create a new migration instead.

Exception:

A historical migration may only be changed if the user explicitly requests it
and there is a clear reason that does not risk existing installations.

Otherwise:

```text
existing migration
        ↓
leave unchanged

new schema change
        ↓
new migration
```

---

## 7. Never Assume an Empty Database

Even when developing against a new local installation, migrations must assume
that another deployment may contain existing data.

Before adding a field or constraint, ask:

```text
Will existing rows remain valid?

Does this new column require a default?

Can it initially be nullable?

Does existing data violate a new uniqueness rule?

Will a foreign key be valid for all existing rows?

Does data require a backfill?

Could encrypted values become unreadable?
```

A migration that works only on an empty database is not automatically safe.

---

## 8. Adding Columns

For a new column, determine:

```text
nullable?
default?
server default?
application default?
existing-data backfill?
index?
unique?
foreign key?
encrypted?
```

Be especially careful with:

```text
nullable=False
unique=True
foreign keys
encrypted values
```

For an existing populated table, adding:

```python
nullable=False
```

without a valid migration strategy may fail.

Prefer an explicit staged migration when necessary:

```text
add nullable column
        ↓
backfill existing records
        ↓
validate data
        ↓
make non-nullable
```

when appropriate.

Do not apply this pattern mechanically if a simpler safe migration exists.

---

## 9. Removing Columns or Tables

Treat destructive schema changes as high risk.

Before removing data, determine:

```text
Is the field truly unused?

Does any route use it?

Does any template use it?

Does any background task use it?

Does any export/import depend on it?

Does any external integration depend on it?

Does historical data still matter?
```

Do not remove persisted data merely because no obvious reference appears in one
file.

Use targeted repository search.

For destructive migrations, consider using:

```text
/careful
```

before implementation.

---

## 10. Relationships and Foreign Keys

When modifying relationships, inspect both sides.

Consider:

```text
foreign key behavior
relationship cascade
delete behavior
nullable relationships
orphan handling
existing rows
ownership/security implications
```

Do not introduce a cascade delete without understanding its effect.

For example:

```text
User
  ↓
VaultEntry
```

may have security and ownership implications beyond database integrity.

Database relationships are not merely implementation details.

---

## 11. Unique Constraints

Before adding a unique constraint:

1. inspect current data assumptions;
2. determine whether duplicates can already exist;
3. define how duplicates would be handled;
4. ensure application validation matches database enforcement.

Do not rely only on application checks for invariants that must be guaranteed by
the database.

Likewise, do not add a database uniqueness constraint without considering
existing records.

---

## 12. Indexes

Add indexes only when there is a concrete query or integrity requirement.

Do not add indexes speculatively.

Consider indexing fields commonly used for:

```text
lookup
filtering
foreign keys
ordering on large datasets
unique identity
```

Document why a new index is required when the reason is not obvious.

---

## 13. Encrypted Database Fields

If the affected model stores secret material, also read:

```text
docs/decisions/ADR-004-secrets-at-rest.md
```

Determine which encryption domain protects the value.

Current examples include:

```text
SECRET_KEY_DB
VAULT_KEY
```

Do not assume they are interchangeable.

Never migrate encrypted values by treating ciphertext as ordinary plaintext.

Before modifying encrypted storage, determine:

```text
current encryption mechanism
existing ciphertext format
decryption path
new encryption path
migration strategy
rollback behavior
failure behavior
```

Do not inspect real secret values simply to understand the format.

---

## 14. Vault Database Changes

Vault is a higher-sensitivity subsystem.

For Vault-related database changes also read:

```text
docs/systems/vault.md
docs/decisions/ADR-004-secrets-at-rest.md
```

Pay special attention to:

```text
VaultEntry.uuid
password_enc
notes_enc
custom encrypted fields
owner_id
shared
group relationships
VaultSyncConfig
KeePass synchronization
```

Do not break compatibility with Vault ↔ KeePass synchronization accidentally.

A database change to Vault may affect:

```text
database
UI
import
export
sync
authorization
encryption
```

Treat it accordingly.

---

## 15. VirusTotal and CSIRT Shared Data

VirusTotal and CSIRT share parts of their IoC metadata architecture.

Before modifying IoC-related persistence, inspect:

```text
docs/systems/virustotal.md
docs/systems/csirt.md
```

and the relevant shared models/mixins.

Do not duplicate fields that already belong to a shared model or mixin.

Changes to shared IoC persistence may affect both subsystems.

---

## 16. Umbrella Jobs and Results

Umbrella persistence represents operational jobs and external mutations.

Before changing Umbrella job/result models, read:

```text
docs/systems/umbrella.md
```

Consider:

```text
job progress
partial completion
result ownership
external side effects
restart behavior
historical records
```

Do not treat job rows as disposable temporary data without verifying their role.

---

## 17. Authorization Impact

Database changes can alter security behavior.

If modifying:

```text
user ownership
UserTool
shared flags
administrator state
resource relationships
permission configuration
```

also read:

```text
docs/decisions/ADR-003-tool-authorization-model.md
docs/systems/auth.md
```

Do not assume database integrity equals authorization correctness.

For example:

```text
resource.owner_id exists
```

does not automatically mean routes correctly enforce ownership.

---

## 18. Creating the Migration

Use the project's Flask-Migrate/Alembic workflow.

Typical workflow:

```bash
flask db migrate -m "describe change"
```

Then inspect the generated migration before applying it.

Do not blindly execute:

```bash
flask db upgrade
```

without reading the generated migration for non-trivial changes.

Review:

```python
def upgrade():
    ...

def downgrade():
    ...
```

Check that Alembic detected only the intended schema changes.

Autogeneration may include unintended changes.

---

## 19. Migration Scope

A migration should contain only the database changes required for the task.

Do not mix:

```text
unrelated schema cleanup
unrelated renames
old technical debt
formatting changes
experimental fields
```

into the same migration.

Small, focused migrations are easier to:

```text
review
test
understand
rollback
diagnose
```

---

## 20. Upgrade Validation

After creating the migration, test the upgrade against a disposable/test
database.

Validate:

```text
migration completes
application starts
expected tables/columns exist
existing modeled relationships work
affected routes load
writes succeed
reads succeed
```

Do not validate schema changes against production/runtime data unless explicitly
requested.

---

## 21. Downgrade Validation

Review whether:

```bash
flask db downgrade
```

can reasonably restore the previous schema.

Not every data transformation is perfectly reversible.

If downgrade causes unavoidable data loss, state it explicitly.

Do not create a fake downgrade that appears reversible but corrupts data.

---

## 22. New Installation Behavior

This repository currently contains startup logic that can initialize databases.

Before modifying database initialization, inspect:

```text
run.py
server.py
```

Do not assume they behave identically.

If changing installation/bootstrap behavior, explicitly verify:

```text
fresh database
existing database
Alembic version state
migration upgrade path
```

Avoid introducing another initialization strategy without resolving how it
interacts with the existing ones.

---

## 23. Migration and db.create_all()

The project may currently use `db.create_all()` in some startup paths.

Do not use `db.create_all()` as a replacement for Alembic migrations when
implementing schema evolution.

The accepted architecture is:

```text
SQLAlchemy model
        +
Alembic migration
```

`db.create_all()` may participate in fresh installation behavior, but it does
not replace migration history.

---

## 24. Migration Naming

Use concise migration descriptions.

Good:

```text
add vault sync config
add notification read state
add umbrella job index
```

Avoid vague names such as:

```text
update
changes
fix database
new fields
migration 2
```

Migration filenames may include generated revision identifiers; the human
message should still explain the change.

---

## 25. Verify Git State Before Editing

Before a non-trivial database change, run:

```bash
git status --short
```

If affected models or migrations already contain uncommitted changes:

```text
do not overwrite them
do not reset them
do not revert them
```

Account for existing work.

Do not use destructive Git commands without explicit user approval.

---

## 26. Requirements Changes

A normal SQLAlchemy/Alembic change should not require a new Python dependency.

Before adding a package for database work:

1. inspect `requirements.txt`;
2. determine whether SQLAlchemy/Alembic already support the requirement;
3. justify any new dependency.

Do not introduce another migration or ORM library.

---

## 27. Tests

Database changes should preferably include or update tests for affected
behavior.

Depending on the change, test:

```text
model creation
default values
constraints
relationships
authorization behavior
migration upgrade
migration downgrade
existing-data compatibility
encrypted-field handling
```

If there is no automated coverage for the affected area, state that explicitly.

Do not claim migration safety solely because it ran once on an empty database.

---

## 28. Documentation

After implementation, determine whether these require updates:

```text
docs/systems/<subsystem>.md
docs/technical-debt/current.md
docs/PROJECT_MAP.md
docs/decisions/
```

Examples:

```text
new persisted subsystem behavior
→ update docs/systems/

technical debt fixed
→ update docs/technical-debt/current.md

new architectural database policy
→ new ADR

new model/module boundary
→ update docs/PROJECT_MAP.md
```

Do not create a new ADR for ordinary schema changes.

## 30. Required Pre-Implementation Summary

Before implementing a non-trivial database change, summarize:

```md
## Database Change

### Objective

What persistent behavior needs to change.

### Current Model

Which models/tables currently implement it.

### Proposed Schema Change

Exact fields, relationships, constraints, or indexes to change.

### Existing Data Impact

How existing rows remain compatible or how they will be migrated.

### Migration

What the Alembic upgrade and downgrade must do.

### Security Impact

Authorization, ownership, secrets, or encrypted-data implications.

### Risks

Concrete migration/regression risks.

### Validation

How the schema and application behavior will be tested.
```

Keep this summary proportional to the change.

A trivial index addition does not require an essay.

---

## 31. Completion Checklist

Before declaring a database change complete, verify:

```text
[ ] Current model was inspected
[ ] Relevant system documentation was read
[ ] Relevant ADRs were respected
[ ] Technical debt interaction was checked
[ ] Existing data was considered
[ ] SQLAlchemy model was updated
[ ] New Alembic migration was created
[ ] upgrade() was reviewed
[ ] downgrade() was reviewed
[ ] Migration scope contains no unrelated changes
[ ] Application starts after upgrade
[ ] Affected reads/writes work
[ ] Authorization remains correct
[ ] Encrypted values remain protected, if applicable
[ ] Tests were run or missing coverage was reported
[ ] Documentation was updated if behavior changed
[ ] Final diff was reviewed
```

---

## 32. Core Rule

Never treat a database migration as merely:

```text
change model
run migration
done
```

For this project, a database change is:

```text
schema
+
existing data
+
application behavior
+
authorization
+
security
+
migration history
+
validation
```

Preserve all of them.
